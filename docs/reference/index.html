Ocarina of Time (Switch 2) — data notes

The full write-up of solved problems, the code patch and investigation methods is in FINDINGS.md. This page is a short overview plus browsable references.

What has been worked out about the game's save data, story progress and code while building ootmenu, a gz-style practice menu for the Lichii emulator. Everything here applies to program 0400486024DEC000, update v131072, main build E0F3CCFA…; other versions differ.

Addresses are offsets into the main module ("main+0x…"). Field hashes are MurmurHash3_32 (seed 0) of the field's name, shown as hex.

Save data (GameData)

All saved state lives in GameData fields, each keyed by the hash of its name. The full list, with types and defaults, ships in the game: romfs/GameData/GameDataList.Product.110.byml.zs (a big-endian BYML, zstd-compressed with zs.zsdic from romfs/Pack/ZsDic.pack.zs). It holds about 15,000 fields with 32-bit keys plus 11,657 Bool64bitKey flags. Browse them on the save fields page.

Types that matter

  • Bool / Int / UInt / Float: plain values (flags, counts, capacities).
  • Enum: the value is the hash of a choice name (for example Strength: None/Low/Middle/High; bottle contents).
  • BoolExp: a formula over other fields, evaluated by the game (for example "quest is at or past stage X").
  • Struct: a named group of other fields (for example PlayerStatus, ActionGuide_IsEnd).
  • String64: up to 63 characters of text (equipped gear names, current map).

In memory

GameData keeps a type list of (type vtable, count, objects, hash table) entries. Objects of one type are a fixed size apart (Int and Float 0x28, Enum 0x38, Bool 0x18). The current value sits at +0x1C with a copy at +0x20 (Bool: +0x16 and +0x17); write both. The hash table maps field hash → object index. Every object also says whether it is saved: a save file index at +0x10 (-1 not saved, 0 the save slot) and reset bits at +0x08 (bit 0: cleared on an area change, inferred). About 9,870 of the 11,292 Bools are saved and kept across areas; the save fields page shows both and can list only those.

Save files

%APPDATA%\eden\nand\user\save\0000000000000000\<user>\0400486024DEC000\slot_NN\progress.sav. From offset 0x20 it is a table of (hash u32, value u32) pairs; for String64 fields the value is the file offset of a 64-byte text slot. There is no checksum.

Names

The game stores hashes, not names. Names were recovered by hashing every string found in the game's scripts and data (event flows, logic, sequences, UI) and matching against the field list: about 4,600 real names such as Get_StoneOfForest_IsCompleted_Exp or PouchData.Item_Ocarina_Fairy.StockNum. A further 2,568 names come from strings in the game's memory while it runs (data/memory_names.json), so about 7,160 of the ~15,000 fields are named. Another ~3,600 fields have readable titles from the onif save editor, matched by exporting its demo save with known changes and diffing the result.

Useful name patterns:

  • IsGet.<item>: item acquired (also songs: IsGet.Item_Melody_SariaSong).
  • PouchData.<item>.StockNum: number owned.
  • HavePlayedEvent.<event>, HaveTalked_Special.<npc>_<event>: event and conversation history.
  • Step_<quest>: quest stage (see below).
  • Sequence_*, UI_*: runtime switches.

Story progress

Each quest is one Enum field holding its current stage. 45 exist; see quests. Setting "played event" flags alone does nothing; setting the stage does, after a loading zone. Example: the Deku Tree is Step_Get_StoneOfForest, from NotReady to Complete.

Tutorial guides

ActionGuide_IsEnd records which tutorial screens have been seen. Some HUD features stay off until theirs has been seen. The D-pad only appears after the Navi guide, normally shown on entering the Deku Tree. See tutorials.

Items and equipment

  • An item needs PouchData.<item>.StockNum and its IsGet.<item> flag to show on the item screen. The L/R quick menus only open with two or more items acquired.
  • Equipped gear is the struct PlayerStatus: EquipWeapon, EquipShield, EquipArmor, EquipBoot, EquipHeadArmor, EquipHandArmor, EquipOcarina (String64, e.g. Item_Ocarina_Fairy).
  • Link's gear is separate objects. Pouch counts, IsGet and PlayerStatus.Equip* are only data; the usable item exists once the game calls main+0x2df6c80(equipment component, slot), which reads the slot's PlayerStatus.Equip* name and creates the item on Link (slot 0xd = EquipOcarina; the full set is applied in slots 0, 6–10, 0xd–0x10). Link's equipment component has vtable main+0x4b49698 and points back at Link's actor at +0x18. An area reload does not re-run it. Without it the D-pad shows the ocarina but the button does nothing.
  • Giving the ocarina live (verified, what ootmenu does): set ActionGuide_IsEnd.Navi (the D-pad needs it) and PlayerStatus.EquipOcarina; add it with the game's add-to-inventory code as the Saria scene does (IsEquipDirect = false); call main+0x2df6c80(component, 0xd); then redraw the HUD with the PlayerStatus screen's virtual method 98 (+0x310 = main+0xa77ff0(screen)), which is what pause/unpause runs. All three calls run on the game's thread through ootmenu's patch.
  • Taking it away (verified): the game's AddOrRemovePouchContent node with Num < 0 calls main+0x33a4fa0(pouch manager, &name, count, 0, 0, 0) (the add function with a negative count does nothing). With EquipOcarina emptied first, main+0xf201b0(owner, 0) (the full gear re-apply the remove code also uses; owner = vtable main+0x4bdfe68, component at +0x470) takes the ocarina off Link; the single-slot call does not. Then the HUD redraw, and clear IsGet.
  • PlayerStatus.Equip* follow what the player equips in the pause menu, live. To take worn gear off Link, empty its field and call main+0xf201b0(owner, 0).
  • Item buttons are four Enum fields (names not recovered): 0x6bee602d, 0x76f85e6d, 0xa0029837, 0xbc32ce24. Their choices are the assignable items (Empty, DekuStick, SlingShot, HeavyBoot, bottles, masks, ...). The in-game item wheel keeps its own copy and writes it back when it closes.
  • Songs are just their IsGet.Item_Melody_* flags.

Magic

Current magic has a "real" value in the magic meter object (it holds the hashes of Current magic and Magic capacity at +0x38/+0x3C, the value at +0x44). Every frame the game writes clamp(value, 0, capacity) into the save field, so writing only the save field is undone. With capacity 0 there is no meter. Normal meter = 240, double = 480.

Game files

The game ships as a .nup package (layout documented by Hookshot's nx2/nup.py). Most romfs files are zstd with dictionaries from Pack/ZsDic.pack.zs. Event scripts (Event/EventFlow/*.bfevfl, format v0.4) decode with the evfl Python package and list exactly what each scene sets and checks.

Code patches

Lichii applies IPS/IPS32 patches from %APPDATA%\eden\load\0400486024DEC000\<mod>\exefs\E0F3CCFAF50065AE4EA01EB5AEB13B1A45DA3348.ips at game start. Offsets are main offsets + 0x100 (module header). Patches can't take effect in a running game. The gap between the end of main's code (0x3c461d0) and rodata (0x3c47000) is executable and zero-filled; Lichii's own fixes use 0x3c46200–0x3c46278, ootmenu uses 0x3c46400 onwards.

ootmenu's give-item hook (patch v6)

Every frame main+0x3b500a4 locks GameData, applies its command queue (main+0xb99980) and tail-calls the unlock at main+0x3b500dc. The patch redirects that tail call to a routine in the code gap, which unlocks, reads a mailbox field (SimpleIntForMessage3, never saved) with the game's GetInt (main+0x163d20). The game itself also writes that field (its save-date text, main+0x33cc94c, puts the day there), so requests are tagged 0x0CA7 << 16 | IsEquipDirect << 8 | item (or 0x7F = call request) and anything else is left alone. A tagged request is cleared with SetInt (main+0x163b70), and the hook calls the game's add-to-inventory function main+0x110d570 exactly as the OneShotAddOrRemovePouchContent node (used by the Saria scene) does: (pouch manager = *[main+0x4c7e0d0], &name, 0, count, reason, 0, 0, IsEquipDirect, [sp]=0), where name is {char* top; s32 size = 0x80; char buf[]}. This only puts the item in the pouch (count + IsGet); see Items and equipment for making it usable. The hook also sets the SeqOneShotResetPlayerStatus flags (PlayerStatus screen +0x384 = -1, +0x388 = 1); they are consumed but do not redraw the D-pad, and neither does main+0xe35440. Source: tools/hook_asm.py.

The "call a game function" request (patch.call_function: function and arguments in the message scratch Ints) runs main+fn(x0, x1) once on the game's thread; ootmenu uses it for the equip call and the HUD redraw (patch.give_gear). The HUD screen (UI manager *[main+0x4c7e098], screen hash 0x5c7f1c3c) holds the D-pad widget (vtable main+0x4be1068) at +0x330. tools/dpadwatch.py sets GDB write watchpoints on that widget to catch the code that shows it.

Tools (ootmenu/tools)

  • nupfs.py: list and extract files from the .nup.
  • byml.py: read BYML files.
  • evdump.py: decode an event script (what it sets and checks).
  • re64.py: find code that uses a string or function; disassemble with field names shown.
  • snap.py: snapshot every live save field and diff two snapshots.
  • ../flags.py: search and set flags by name in the running game.
